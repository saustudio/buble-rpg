## 1. Философия проекта

- Проект строго ООП. Весь код — в классах.
- Модели анемичные: только данные, без бизнес-логики.
- Вся логика — в сервисах.
- Свободные функции на уровне модуля запрещены полностью.
- Слои разделены: Model / Service / View / DTO. Каждый знает
  только то, что ему положено.
- Один файл = один модуль. Модуль содержит все связанные классы,
  интерфейсы и типы одной темы.
- ECS — симуляция. Сеть — наблюдатель. UI — рендер. Они не
  смешиваются.
- Спецификации слоёв: `spec-ui.md`, `spec-network.md`.
  Дополняют этот документ, не заменяют.

## 2. Архитектура: Model / Service / View

### 2.1. Модель (Model) — анемичная

Хранит **только данные**. Никакой логики.

Разрешено:
- Публичные поля.
- Конструктор с инициализацией полей.
- Геттеры/сеттеры, если нужна валидация при доступе (редко).

Запрещено:
- Методы с бизнес-логикой (`Has...`, `Get...`, `Calculate...`,
  `IsValid`, `Can...`).
- Статические фабрики `FromDto` / `Create` / `From...`.
- Методы `ToDto` / `ToView` / конвертация.
- Зависимости на сервисы.
- Импорты из UI, сети, DTO-пакетов.

Пример:

    export class LootItem
    {
        public Id: string;
        public Name: string;
        public Rarity: ItemRarity;
        public IconRef: string;
        public Requirements: Requirements;
        public Mods: ItemMod[];
        public StatChanges: StatChange[];

        constructor(...) { ... }
    }

### 2.2. Сервис (Service) — вся логика

Выполняет **все операции**: конвертацию, вычисления, координацию
моделей, бизнес-правила.

Разрешено:
- Методы экземпляра.
- Приватные вспомогательные методы.
- Статические методы, если сервис stateless и метод не зависит
  от состояния (редко, предпочтительнее — экземпляр).
- Зависимости через конструктор.
- Чтение и запись полей моделей.

Запрещено:
- Свободные функции рядом с классом.
- Прямой доступ к UI, сети, DOM.
- Знание про ECS-компоненты (кроме сервисов ECS-слоя).

Пример:

    export class LootItemService
    {
        public HasMetRequirements(item: LootItem, stats: EntityStats): boolean { ... }
        public GetExplicitCount(item: LootItem): number { ... }
    }

### 2.3. View — анемичный снимок

Данные для рендера. Формируется сервисом-маппером.

Разрешено:
- `interface` с публичными `readonly` полями.
- Вложенные интерфейсы.
- Type-алиасы для простых типов.

Запрещено:
- Методы.
- Классы (кроме случаев, когда нужна идентичность — редко).
- Логика.

Пример:

    export interface LootItemView
    {
        readonly id: string;
        readonly displayName: string;
        readonly displayIcon: string;
        readonly modLines: readonly ModLineView[];
    }

### 2.4. DTO — анемичный сетевой контракт

Живёт в `shared/protocol/`. Используется и клиентом, и сервером.

Разрешено:
- `interface` с публичными полями.
- Только семантические данные (без css-классов, локализованных
  строк, эмодзи-иконок).

Запрещено:
- Презентационные поля.
- Методы.
- Логика.

### 2.5. Таблица размещения

| Что | Куда |
|---|---|
| Данные | Модель (класс с публичными полями) |
| Бизнес-логика | Метод сервиса |
| Конвертация Dto ↔ Model | Метод сервиса-конвертера |
| Конвертация Model → View | Метод сервиса-маппера |
| Данные для рендера | View-интерфейс |
| Сетевой контракт | DTO-интерфейс |
| Утилита для примитивов | Статический метод класса-утилиты |

## 3. Размещение кода: запрет свободных функций

### 3.1. Правило

Любая функция должна быть методом подходящего класса.
Свободные функции на уровне модуля запрещены полностью.

### 3.2. Что запрещено

- `export function xxx(...) { ... }`
- `function xxx(...) { ... }` вне класса.
- `export const xxx = (...) => ...`
- `const xxx = (...) => ...` вне класса.
- Анонимные IIFE, если в них есть логика, которую можно
  разместить в классе.

### 3.3. Куда переносить функцию

| Роль функции | Куда |
|---|---|
| Операция над одной моделью | Метод сервиса этой модели |
| Операция над несколькими моделями | Метод сервиса-координатора |
| Конвертация Dto → Model | Метод сервиса-конвертера |
| Конвертация Model → Dto | Метод сервиса-конвертера |
| Конвертация Model → View | Метод сервиса-маппера |
| Конвертация Dto → View | Метод сервиса-маппера |
| Форматирование значения | Метод сервиса-маппера или класса-утилиты |
| Утилита для примитивов | Статический метод класса-утилиты |
| Обработчик события | Метод класса, где событие обрабатывается |
| Фабрика объектов | Метод сервиса-фабрики |

### 3.4. Классы-утилиты

Для примитивов (числа, строки, даты) — классы-утилиты со
статическими методами:

    export class MathUtils
    {
        public static Clamp(value: number, min: number, max: number): number
        {
            return Math.max(min, Math.min(max, value));
        }
    }

    export class StringUtils
    {
        public static Capitalize(value: string): string { ... }
        public static Truncate(value: string, max: number): string { ... }
    }

Не создавать свободные функции вида `clamp(...)`, `capitalize(...)`.


### 3.5. Когда метод не создаётся

Метод не создаётся, если **все** условия выполнены:

1. Вызывается ровно из одного места.
2. Тело — одно выражение (не блок с несколькими шагами).
3. Выражение короче ~100 символов и без вложенности
   глубже 2 уровней.
4. Инлайн не требует пояснений — смысл ясен из контекста.
5. Имя метода не добавляет информации, которой нет в контексте
   вызова.

Если хотя бы одно условие не выполнено — метод создаётся.

Примеры:

Плохо — метод-обёртка без логики, вызывается из одного места:
    private GetEquipment(entity: EntityId): Equipment
    {
        return World.GetComponent(entity, EquipmentComponent)!.Equipment;
    }

    // вызов:
    const eq = this.GetEquipment(entity);

    // лучше:
    const eq = World.GetComponent(entity, EquipmentComponent)!.Equipment;

Плохо — метод-обёртка, вызывается из одного места:
    private CollectLootItems(entities: EntityId[]): Item[]
    {
        const result: Item[] = [];
        for (const entity of entities) { ... }
        return result;
    }

    // лучше — инлайн одной операцией:
    const lootList = deathList.flatMap((entity) =>
        EquipmentService.All(World.GetComponent(entity, EquipmentComponent)!.Equipment)
    );

## 4. Организация файлов: один файл = один модуль

### 4.1. Принцип

Один файл = один модуль. Модуль содержит все связанные классы,
интерфейсы и типы, которые логически принадлежат одной теме.

Не создавать отдельный файл на каждый класс. Группировать по смыслу.

### 4.2. Что считается «связанным»

Связанные — это классы и типы, которые:

- относятся к одной сущности или одному сценарию;
- используются вместе;
- меняются вместе;
- не имеют смысла друг без друга.

Не связанные — это классы, которые:

- используются в разных частях проекта независимо;
- имеют разный жизненный цикл;
- могут быть переиспользованы отдельно.

### 4.3. Пример: диалог лута

Плохо — файл на каждый класс:

    ui/dialogs/
      LootDialog.ts
      LootDialogState.ts
      LootItemView.ts
      ModLineView.ts
      ChangeLineView.ts
      LootItemViewService.ts
      LootDialogStateService.ts

Хорошо — один модуль на диалог:

    ui/dialogs/
      LootDialog.ts    ← всё, что относится к диалогу лута

Внутри `LootDialog.ts`:

    // ─── View-типы ───
    export type CompareStyle = "better" | "worse" | "equal";

    export interface ModLineView { ... }
    export interface ChangeLineView { ... }
    export interface LootItemView { ... }
    export interface LootDialogState { ... }

    // ─── Сервис-маппер ───
    export class LootItemViewService { ... }
    export class LootDialogStateService { ... }

    // ─── Dialog ───
    export class LootDialog extends Dialog { ... }

### 4.4. Пример: модель лута

Плохо:

    models/
      LootItem.ts
      Requirements.ts
      ItemMod.ts
      StatChange.ts
      ItemRarity.ts

Хорошо:

    models/
      LootItem.ts    ← модель и все её составные части

Внутри:

    export enum ItemRarity { ... }
    export enum ModKind { ... }
    export enum ModUnit { ... }

    export class Requirements { ... }
    export class ItemMod { ... }
    export class StatChange { ... }
    export class LootItem { ... }

### 4.5. Когда всё-таки разбивать на файлы

Разбивать нужно, если:

1. **Класс переиспользуется в разных модулях независимо.**
   Например, `Requirements` используется и в `LootItem`, и в
   `QuestReward`, и в `TradeOffer`. Тогда `Requirements.ts` —
   отдельный модуль.

2. **Модуль разрастается.** Если файл превышает ~500–700 строк
   и внутри чётко видны независимые группы — можно разделить по
   группам. Но сначала подумать, не является ли это признаком
   плохой декомпозиции.

3. **Циклические зависимости.** Если два класса ссылаются друг
   на друга и не могут жить в одном файле — разделить, но это
   признак проблемы в дизайне.

4. **Разные слои.** Model не должен лежать в одном файле с
   Service, если Service зависит от инфраструктуры, которой нет
   в Model. Но если Service — это конвертер для этой же Model,
   они могут жить рядом.

### 4.6. Именование файлов

- Имя файла = имя главного класса или главной темы модуля.
- `LootDialog.ts` — если главное в модуле — диалог.
- `LootItem.ts` — если главное — модель.
- `LootPreviewService.ts` — если главное — сервис.
- `index.ts` — только для реэкспорта из папки, не для логики.

### 4.7. Что запрещено

- Файл на каждый класс без причины.
- Файл на каждый интерфейс.
- Файл на каждый enum.
- Файл на каждую константу.
- Пустые файлы-реэкспорты (`export * from "./Xxx"`) без причины.

### 4.8. Что разрешено

- Один файл — один модуль со всеми связанными классами.
- Один файл — одна сущность + её сервисы + её View + её DTO,
  если они образуют единый модуль.
- Реэкспорт через `index.ts` в папке, если это удобно для импорта.

## 5. Нейминг классов и суффиксов

### 5.1. Суффиксы классов

| Суффикс | Роль | Пример |
|---|---|---|
| `Model` | Анемичная модель (редко, обычно без суффикса) | `LootItem` |
| `Service` | Сервис с логикой | `LootItemService` |
| `Converter` | Конвертация Dto ↔ Model | `LootItemConverter` |
| `ViewService` | Конвертация Model → View | `LootItemViewService` |
| `View` | Интерфейс снимка для рендера | `LootItemView` |
| `State` | Корневой View-тип диалога | `LootDialogState` |
| `Dto` | Сетевой контракт | `LootItemDto` |
| `Message` | Сетевое сообщение верхнего уровня | `LootDialogMessage` |
| `Dialog` | UI-диалог | `LootDialog` |
| `Component` | ECS-компонент | `HealthComponent` |
| `System` | ECS-система | `DamageSystem` |
| `Utils` | Класс утилит | `MathUtils` |

### 5.2. Запрещённые суффиксы

- `Manager` — слишком размыто. Использовать `Service`.
- `Helper` — слишком размыто. Использовать `Utils` или `Service`.
- `Handler` — только для обработчиков событий, если действительно
  обработчик. В остальных случаях — `Service`.


### 5.3. Имена методов

Стиль — C#-подобный. Все методы в `PascalCase`, независимо от
видимости. Никаких исключений для приватных.

- Публичные методы: `PascalCase` — `ToView`, `BuildState`, `Resolve`.
- Приватные методы: `PascalCase` — `MapMod`, `FormatValue`, `IconUrl`.
- Защищённые методы: `PascalCase` — `RenderItem`.

Глагол в начале: `Get...`, `Set...`, `Has...`, `Is...`,
`Build...`, `Resolve...`, `Convert...`, `Format...`, `Map...`,
`Render...`, `To...`, `From...`.

Не использовать `Process`, `Handle`, `Do` без уточнения.

Исключений для `camelCase` нет. Не `mapMod`, а `MapMod`.
Не `iconUrl`, а `IconUrl`. Не `rarityClass`, а `RarityClass`.

Публичные поля  `PascalCase`:
- `public Id: string`

Приватные и локальные переменные `camelCase`
- `private readonly itemsEl: HTMLElement`
- `const itemViewService = new LootItemViewService()`

## 6. Конвертация между слоями

### 6.1. Правило

Конвертация — всегда метод класса. Никогда свободная функция.

### 6.2. Куда что конвертируется

| Направление | Класс | Метод |
|---|---|---|
| Dto → Model | `XxxConverter` | `FromDto(dto): Model` |
| Model → Dto | `XxxConverter` | `ToDto(model): Dto` |
| Model → View | `XxxViewService` | `ToView(model): View` |
| Dto → View | `XxxViewService` | `ToViewFromDto(dto): View` |
| Model → State | `XxxStateService` | `ToState(model, onPick): State` |
| Dto → State | `XxxStateService` | `ToState(msg, onPick): State` |

### 6.3. Где живёт конвертер

Рядом с моделью, в том же модуле. Не в модели. Не в UI.

### 6.4. View-модель не конвертируется обратно

View → Model не бывает. View — только для чтения. Если нужна
обратная конвертация — это уже не View, а DTO или команда.

## 7. UI-слой

Полная спецификация — `spec-ui.md`. Здесь ключевое.

### 7.1. Dialog — чистый View

- Не знает про ECS, World, EntityId.
- Не знает про сеть.
- Принимает `State` (View-модель) через `OnOpen`.
- Считает только DOM. Никакой логики.
- Локальные View-типы — в том же файле, если используются только
  этим диалогом.

### 7.2. Маппер DTO → State

- Класс-сервис: `XxxStateService` или `XxxViewService`.
- Не знает про DOM.
- Не знает про ECS.
- Чистые методы без побочных эффектов.

### 7.3. Фасад UI

- `UI.Register(dialog)`, `UI.Open(key, state)`, `UI.Close(key)`.
- Управляет стеком диалогов и паузой.
- Не знает про конкретные диалоги.

### 7.4. Запрещено в UI

- Импорт `World`, `EntityId`, компонентов.
- Вызов `World.GetComponent(...)`.
- Свободные функции для форматирования.
- Прямое управление `GameState`.

## 8. Сетевой слой

Полная спецификация — `spec-network.md`. Здесь ключевое.

### 8.1. Система vs сервис

- **ECS-система:** работает через компоненты, не хранит своего
  состояния, тикает в общем цикле.
- **Сетевой сервис:** хранит своё состояние (retryQueue, ackTracker),
  работает с транспортом, тикает отдельно или по событиям.

### 8.2. Что запрещено

- ECS-система импортирует сетевые типы.
- ECS-система вызывает `transport.Send(...)`.
- Сетевой сервис пишет в ECS-компоненты.
- Сетевой сервис вызывает бизнес-логику ECS напрямую.
- Таймауты в сетевом слое.

### 8.3. Что разрешено

- ECS-система эмитит события в шину.
- ECS-система создаёт компоненты с полями для сети (`dirty`,
  `ExpiresAt`, `Claimed`).
- Сетевой сервис читает компоненты.
- Сетевой сервис пишет в свои структуры.
- Сетевой сервис эмитит события в шину.

### 8.4. Состояние vs событие

- Всё, что важно не потерять, — состояние (компонент).
- Событие — оптимизация для мгновенной реакции.
- UI открывается по состоянию, не по событию.

## 9. ECS-слой

### 9.1. Система

- Работает через `EntityQuery`.
- Не хранит своего состояния вне компонентов.
- Пишет только в компоненты.
- Не знает про UI, сеть, DOM.

### 9.2. Компонент

- Анемичный. Только поля.
- Никакой логики, кроме тривиальных методов доступа (если нужно).

### 9.3. Что запрещено

- `import` из UI.
- `import` из сетевого слоя.
- Прямые вызовы `UI.Open`, `transport.Send`.
- Хранение состояния вне компонентов (кэши, очереди) без
  крайней необходимости.

## 10. Проверка при ревью

Пройти по файлу и проверить:

1. Есть ли `function` вне класса? → нарушение, перенести.
2. Есть ли `const fn = () => ...` вне класса? → нарушение, перенести.
3. Есть ли методы с логикой в моделях? → нарушение, перенести
   в сервис.
4. Есть ли статические фабрики `FromDto` / `Create` на моделях?
   → нарушение, перенести в `Converter`.
5. Есть ли `ToDto` / `ToView` на моделях? → нарушение, перенести
   в `Converter` / `ViewService`.
6. Есть ли импорты из другого слоя, которые не положены?
   (UI → ECS, ECS → UI, Model → UI и т.п.) → нарушение.
7. Есть ли презентационные поля в DTO? → нарушение, убрать.
8. Есть ли бизнес-данные в View? → норма, View для этого и нужен,
   но без логики.
9. Есть ли свободные константы, которые логически принадлежат
   классу? → перенести в поле класса.
10. Есть ли файл на один класс без причины? → объединить с
    модулем.
11. Есть ли класс, переиспользуемый независимо, но лежащий в
    чужом модуле? → вынести в отдельный файл.
12. Есть ли метод, который:
    - вызывается ровно из одного места,
    - тело — одно выражение,
    - выражение короче ~100 символов и без вложенности глубже 2 уровней,
    - имя не добавляет информации?
    → нарушение, инлайнить.
